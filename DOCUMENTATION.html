1. Overview & Architecture

This is a Python Azure Functions app (v2 programming model, azure.functions) with no separate web framework. It has three triggers:

  • HTTP POST /api/send-customer-emails — reads eligible customers for a campaign from Databricks, renders the campaign's HTML template per recipient, and sends via Azure Communication Services (ACS) SMTP.
  • Timer trigger (TIMER_SCHEDULE, default daily 8am UTC) — runs the same send logic automatically for the default campaign.
  • HTTP GET/POST /api/unsubscribe (anonymous auth) — the landing page behind the email's "Unsubscribe" link. GET shows a confirm page; POST (the confirm button) records the opt-out in Unity Catalog.
Databricks Unity Catalog (claraport_ws) ├─ prd_viasmiles_email.customer (production recipients) └─ viasmiles_campaigns.customer_test (safe test recipients) └─ viasmiles_campaigns.unsubscribe_list (opt-out log, shared across campaigns) │ │ fetch_customers() — LEFT ANTI JOIN excludes unsubscribed emails ▼ send_customer_emails (HTTP trigger, also daily timer) │ renders templates/<campaign>.html with {{first_name}} {{last_name}} │ {{clinic_city}} {{clinic_phone}} {{booking_link}} {{unsubscribe_link}} ▼ Azure Communication Services SMTP (smtp.azurecomm.net:587) ▼ Recipient inbox — clicks "Unsubscribe" in the footer ▼ GET /api/unsubscribe → confirm page (HMAC token verified, no DB write yet) │ recipient clicks "Confirm unsubscribe" ▼ POST /api/unsubscribe → MERGE INTO unsubscribe_list (idempotent) ▼ Next send excludes this email automatically (anti-join)

Authentication throughout uses one shared Microsoft Entra ID (Azure AD) service principal for both Databricks (auth_type="azure-sp-m2m") and ACS SMTP (the SMTP "password" is the raw Entra client secret; ACS exchanges it for a token server-side). Secrets are intended to live in Azure Key Vault, fetched via the Function App's managed identity — see §12 for the current interim workaround.

3.4 Seed a test row

INSERT INTO claraport_ws.viasmiles_campaigns.customer_test (fname, lname, email)
VALUES ('Test', 'User', 'jvm@analyticsintellect.com');
Why a separate unsubscribe_list table instead of a boolean column? It gives a durable, queryable log of who opted out, when, and from which campaign/source — not just a flag that can be silently overwritten. fetch_customers() does a LEFT ANTI JOIN against it so opt-outs apply across every campaign automatically.

4. Campaigns & Templates

campaigns.py is the single place that maps a campaign id to its data source and its template:

CAMPAIGNS = {
    "viasmiles_acquisition_v1": {
        "schema": "prd_viasmiles_email",
        "table": "customer",
        "template": "viasmiles_acquisition_email_v1.1.html",
        "subject": "Your free implant consultation, 3D CT scan included",
        "merge_tags": {
            "clinic_city": "Columbus",
            "clinic_phone": "(614) 999-1500",
            "booking_link": "https://viasmiles.com/book-consultation/",
        },
    },
    "viasmiles_test": { ... points at viasmiles_campaigns.customer_test ... },
}

Merge tags filled in at send time, per recipient, from the Databricks row plus the campaign config:

TagSource
{{first_name}}customer.fname (falls back to "there" if blank)
{{last_name}}customer.lname
{{clinic_city}}, {{clinic_phone}}, {{booking_link}}Static per campaign, from campaigns.py
{{unsubscribe_link}}Generated per recipient: HMAC-signed token + APP_BASE_URL

Trigger a specific campaign manually with a query parameter:

curl -X POST "https://viasmiles-email-function.azurewebsites.net/api/send-customer-emails?campaign=viasmiles_acquisition_v1&code=<function-key>"

If TEST_MODE=true is set as an app setting, the campaign is force-redirected to viasmiles_test regardless of the query parameter — a safety switch so a misfired production trigger can't email the real list.

5. Unsubscribe Flow (CTA click → database)

  1. Email footer contains: <a href="{{unsubscribe_link}}">Unsubscribe</a> (see templates/viasmiles_acquisition_email_v1.1.html, footer section).
  2. The link format: {APP_BASE_URL}/api/unsubscribe?email=<url-encoded email>&token=<hmac-sha256 hex>, generated by unsubscribe_utils.generate_token(), keyed by the unsubscribe-signing-key secret.
  3. GET request (the click itself) verifies the token and renders a confirm page — it does not write to the database yet. This is deliberate: corporate email scanners and link-prefetchers follow GET links automatically, which would silently opt people out if a GET alone triggered the unsubscribe.
  4. The recipient clicks "Confirm unsubscribe", which submits a POST with the same email + token.
  5. POST handler re-verifies the token, then calls mark_unsubscribed(email, campaign), which runs a MERGE INTO unsubscribe_list — idempotent, so repeated clicks never create duplicate rows or move the timestamp.
  6. Renders templates/unsubscribe_done.html as the final confirmation page.

Verify a recorded unsubscribe directly in Databricks:

SELECT * FROM claraport_ws.viasmiles_campaigns.unsubscribe_list
WHERE email = 'someone@example.com';

8. Dry Run / Local Test

# Terminal 1 — start the Functions host
func start

# Terminal 2 — trigger a send (reads from whatever TEST_MODE routes to)
curl -i -X POST "http://localhost:7071/api/send-customer-emails"

Expected response: Sent: N, Failed: 0. Failed addresses: []. Full tracebacks for any failure appear in the func start terminal (not in the HTTP response) — this is the fastest way to debug locally, since Azure's own remote log streaming is unreliable on a Linux Consumption plan (see §13.1).

To test a specific campaign:

curl -i -X POST "http://localhost:7071/api/send-customer-emails?campaign=viasmiles_acquisition_v1"

To test the unsubscribe landing page:

  1. Open the received email, click "Unsubscribe" in the footer.
  2. Confirm page loads at http://localhost:7071/api/unsubscribe?email=...&token=....
  3. Click "Confirm unsubscribe".
  4. Check the row landed: SELECT * FROM claraport_ws.viasmiles_campaigns.unsubscribe_list WHERE email = '...';
  5. Re-run the curl above — that address should now be excluded (Sent count drops by one).

One-off send without touching Databricks at all (useful for template/layout review):

python send_template_email.py

11. Running in Production

  1. Confirm the service principal has grants on the production table (§3.3) and the campaign schema.
  2. Flip the safety switch off: 
    az functionapp config appsettings set --name <app-name> --resource-group devteam-projectnour-rg \
  --settings TEST_MODE="false"
  3. Confirm ACS_SENDER_ADDRESS is a verified, connected MailFrom address (§13.3) — otherwise sends will bounce with 501 5.1.7 sender domain has not been linked.
  4. Manual send (first production run, supervised): 
    curl -X POST "https://<app-name>.azurewebsites.net/api/send-customer-emails?code=<key>"
  5. From then on, the daily timer trigger (TIMER_SCHEDULE) runs this automatically — no manual trigger needed. Monitor it via Application Insights / Log Analytics (§11.1) rather than the HTTP response, since the timer trigger has no caller to return a response to.

11.1 Monitoring delivery

Communication Services resource → Diagnostic settings → send EmailSendMailOperational and EmailStatusUpdateOperational to a Log Analytics workspace, then query:

ACSEmailStatusUpdateOperational
| where TimeGenerated > ago(1h)
| project TimeGenerated, MessageId, Sender, Recipient, Status, StatusDetail
| order by TimeGenerated desc

Status resolves to Delivered, Bounced, Failed, Suppressed, or Quarantined.

11.2 Rolling back a bad send

There is no built-in "undo a batch send". If a campaign goes out with a mistake, fix the template/config, redeploy, and the next run uses the corrected version — the unsubscribe mechanism is unaffected by template changes.

12. Secrets & Security Notes

Interim App Settings secret override is currently active. The intended design is: secrets live only in Key Vault, and the Function App's managed identity reads them at runtime via DefaultAzureCredential. As of this writing, the managed identity's Key Vault RBAC role assignment (Key Vault Secrets User) has not been successfully granted due to an organizational permissions gap (the account provisioning this app lacks Microsoft.Authorization/roleAssignments/write on the vault scope). As a stopgap, config.py checks for a same-named App Setting override before calling Key Vault: 
def get_secret(name):
    override = os.environ.get(name.upper().replace("-", "_"))
    if override:
        return override
    return _get_client().get_secret(name).value

This means AAD_CLIENT_SECRET_VALUE and UNSUBSCRIBE_SIGNING_KEY currently exist in plaintext in the Function App's App Settings (encrypted at rest by Azure, but visible to anyone with Reader access to the Function App resource — a broader audience than Key Vault's RBAC would normally allow).

Action item: once someone with Owner / User Access Administrator on the subscription or resource group grants the managed identity (principalId, see az functionapp identity show) the Key Vault Secrets User role on Email-Vault, remove the two App Settings overrides:

az functionapp config appsettings delete --name <app-name> --resource-group devteam-projectnour-rg \
  --setting-names AAD_CLIENT_SECRET_VALUE UNSUBSCRIBE_SIGNING_KEY

No code change is needed to revert — get_secret() automatically falls through to Key Vault once the overrides are gone.

12.1 Other notes

  • Never commit local.settings.json or .env — both are gitignored.
  • The unsubscribe route is intentionally AuthLevel.ANONYMOUS (recipients have no function key) — but it only ever writes a row keyed by an HMAC-verified email; it cannot be used to unsubscribe an arbitrary address without a valid signed token for that exact address.
  • The send-customer-emails route requires a function key (AuthLevel.FUNCTION) — don't expose that key in client-side code or public docs/screenshots.

14. Adding a New Clinic / Campaign

  1. Create its Unity Catalog table (own schema or share viasmiles_campaigns), e.g.: 
    CREATE TABLE claraport_ws.viasmiles_campaigns.customer_exton (
  fname STRING, lname STRING, email STRING
);
GRANT SELECT, MODIFY ON TABLE claraport_ws.viasmiles_campaigns.customer_exton
  TO `d97d0f55-a968-43a0-94c6-5d433ac05874`;
  2. Add a new HTML template under templates/ with the same merge tags ({{first_name}}, {{last_name}}, {{clinic_city}}, {{clinic_phone}}, {{booking_link}}, {{unsubscribe_link}}).
  3. Add an entry to CAMPAIGNS in campaigns.py with that table, template filename, subject, and clinic-specific merge tag values.
  4. Deploy, then test with ?campaign=<new_id> before relying on the daily timer (which only runs DEFAULT_CAMPAIGN unless you add additional timer triggers or a multi-campaign loop in function_app.py).

The shared unsubscribe_list table means an opt-out from any clinic's email automatically excludes that address from every other campaign's sends too — there is currently no per-clinic-only opt-out; add a WHERE campaign = ... filter to the anti-join in db_utils.fetch_customers() if per-campaign-only opt-outs are ever needed.
