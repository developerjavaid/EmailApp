# ViaSmiles EmailApp — Reference Guide

Azure Function (Python) that reads customer names/emails from Databricks and sends each one an email through Azure Communication Services (ACS), authenticated with a shared Microsoft Entra ID app registration.

See `runbook.html` for the full narrative writeup (including a troubleshooting log of every issue hit during setup). This file is the condensed step-by-step reference.

## Architecture

```
Databricks SQL (claraport_ws.prd_viasmiles_email.customer)
        |  fetch_customers()
        v
send_customer_emails  (Azure Function, GET/POST /api/send-customer-emails, also daily timer)
        |  reads secret from Key Vault (aad-client-secret-value)
        v
Azure Communication Services SMTP (smtp.azurecomm.net:587)
        |
        v
  recipient inbox
```

- **`function_app.py`** — entry point. HTTP route `send-customer-emails` (GET/POST) and an hourly timer trigger (`TIMER_SCHEDULE`, default `0 0 * * * *`), both call `_send_all_customer_emails()`, which sends one throttled batch per clinic (see "Per-clinic throttled sending" below), all clinics in parallel.
- **`db_utils.py`** — Databricks SQL connection + clinic/threshold/customer queries. Auth via Entra service principal, `auth_type="azure-sp-m2m"`.
- **`email_utils.py`** — `send_email()`. Sends via SMTP to ACS; the "password" is the raw Entra client secret (ACS exchanges it for a token server-side — never do a client-side MSAL token exchange here).
- **`config.py`** — `get_secret()`, fetches secrets from Key Vault via `DefaultAzureCredential`.
- **`send_test_email.py`** — standalone script to send a test email to a list of addresses (`TEST_EMAILS`) without touching Databricks.
- **`unsubscribe_utils.py`** — HMAC-SHA256 signing/verification for per-recipient unsubscribe links, keyed by the `unsubscribe-signing-key` Key Vault secret. No per-recipient DB state is needed to issue a link; verification is a pure signature check.
- **`function_app.py`'s `unsubscribe` route** (`GET/POST /api/unsubscribe`, anonymous auth) — `GET` renders a confirm page (`templates/unsubscribe_confirm.html`); `POST` (the confirm button) verifies the token and calls `db_utils.mark_unsubscribed`, then renders `templates/unsubscribe_done.html`. Requiring a POST to actually unsubscribe (rather than acting on the GET) avoids corporate email scanners / link-prefetchers silently opting people out just by following the link.

### Unsubscribe link format

`{APP_BASE_URL}/api/unsubscribe?email=<url-encoded email>&token=<hmac-sha256 hex of lowercased email>`

Generated by `unsubscribe_utils.generate_token(email)` wherever a template is rendered (`send_template_email.py`, `function_app._unsubscribe_link`). `fetch_customers()` excludes anyone with `unsubscribed = true`, so the daily send and the manual `send-customer-emails` route both honor opt-outs automatically.

Required additional setup:

```bash
az keyvault secret set --vault-name email-vault \
  --name unsubscribe-signing-key --value "$(openssl rand -hex 32)"

az functionapp config appsettings set --name ViaSmiles-EmailApp \
  --resource-group devteam-projectnour-rg \
  --settings APP_BASE_URL="https://viasmiles-emailapp.azurewebsites.net"
```

`APP_BASE_URL` also needs exporting locally (or added to `local.settings.json`) for `send_template_email.py` to build working links in local test sends.

One secret carries the whole app: `aad-client-secret-value` in Key Vault — used both for Databricks auth and ACS SMTP auth.

### Per-clinic throttled sending

Each clinic has its own daily and hourly send caps, and its own customer source table/column mapping, both stored in Databricks — nothing is hardcoded in the app.

- **`clinic` table** (`viasmiles_campaigns.clinic`, seeded by `setup_clinic_mapping.py`) — one row per clinic: `clinic_id, name, template_name, from_email, source_table, email_column, first_name_column, last_name_column`. `source_table` is the fully-qualified table the app reads that clinic's customers from; `email_column`/`first_name_column`/`last_name_column` tell the app what those columns are called in that table. Repointing a clinic at a different table, or at a table with different column names, is just an UPDATE to this row — no code change needed.
- **`clinic_threshold` table** (`viasmiles_campaigns.clinic_threshold`, seeded by `setup_threshold_table.py`) — one row per clinic: `clinic_id, daily_limit, hourly_limit`. `daily_limit <= 0` means that clinic is skipped entirely. `hourly_limit` caps how many of the remaining daily budget go out in a single run.
- **`delivery_status` / `delivery_sent_at`** — added automatically (`db_utils.ensure_delivery_columns`, a no-op once they exist) to each clinic's `source_table` the first time it's sent to. `delivery_status = 'sent'` means that row is **never** sent to again, by this app, regardless of date — checked by status only, not by timestamp. `delivery_sent_at` is used only to compute how many of today's `daily_limit` have already gone out (`db_utils.count_sent_today`), so the per-run batch size is `min(daily_limit - sent_today, hourly_limit)`.
- Every clinic with `daily_limit > 0` is processed **in parallel** (`function_app._send_clinic_emails`, one `ThreadPoolExecutor` worker per clinic) — each clinic reads/writes only its own rows (filtered by `clinic_id`), but if two clinics share the same physical `source_table` (as all 5 do today, via `customer_test`), concurrent `UPDATE`s to that table can occasionally hit a Delta Lake write conflict; the affected send is logged as `failed` and simply gets picked up (still `delivery_status` unset) on the next run. Moving a high-volume clinic to its own dedicated table removes this risk entirely.
- With an hourly timer, a clinic with `daily_limit=3000, hourly_limit=1000` sends ~1000 per run until that day's 3000 is used up, then goes quiet until the next calendar day resets `count_sent_today`'s window.
- Initial seed: Columbus (`clinic_id=3`) and Pittsburgh (`clinic_id=4`) at `daily_limit=3000, hourly_limit=1000`; Georgia (1), Ohio (2), Exton (5) at `daily_limit=0` (no sends) until turned on by updating `clinic_threshold`.

## 1. Key Vault & secret

```bash
az keyvault create --name email-vault --resource-group devteam-projectnour-rg \
  --location centralus --enable-rbac-authorization true

az keyvault secret set --vault-name email-vault \
  --name aad-client-secret-value --value "<paste the Secret VALUE, not the Secret ID>"

# your own login, for local dev
az role assignment create --role "Key Vault Secrets User" \
  --assignee jvm@analyticsintellect.com --scope $(az keyvault show --name email-vault --query id -o tsv)

# the Function App's managed identity, for the deployed app
PRINCIPAL_ID=$(az functionapp identity assign --name ViaSmiles-EmailApp \
  --resource-group devteam-projectnour-rg --query principalId -o tsv)
az role assignment create --role "Key Vault Secrets User" \
  --assignee $PRINCIPAL_ID --scope $(az keyvault show --name email-vault --query id -o tsv)
```

> ⚠️ Entra shows a **Secret ID** (GUID) and a **Value** when you create a client secret — you need the Value. It's shown once at creation only. Using the ID instead fails with `AADSTS7000215`.

`setup_keyvault.sh` automates steps 1-5 of the above (interactive prompt for the secret) — run it directly instead if preferred.

## 3. Databricks access

```sql
CREATE SCHEMA IF NOT EXISTS claraport_ws.prd_viasmiles_email;

CREATE TABLE IF NOT EXISTS claraport_ws.prd_viasmiles_email.customer (
  fname STRING,
  email STRING,
  unsubscribed BOOLEAN,
  unsubscribed_at TIMESTAMP
);
```

> If the table already exists from before the unsubscribe feature, add the two columns instead:
> `ALTER TABLE claraport_ws.prd_viasmiles_email.customer ADD COLUMNS (unsubscribed BOOLEAN, unsubscribed_at TIMESTAMP);`

1. Add the service principal (client ID above) to the Databricks workspace: **Admin Settings → Identity and access → Service principals**.
2. Grant **Can Use** on the SQL Warehouse: **SQL Warehouses → warehouse → Permissions**.
3. Grant Unity Catalog data access:

```sql
GRANT USE CATALOG ON CATALOG claraport_ws TO `d97d0f55-a968-43a0-94c6-5d433ac05874`;
GRANT USE SCHEMA ON SCHEMA claraport_ws.prd_viasmiles_email TO `d97d0f55-a968-43a0-94c6-5d433ac05874`;
GRANT SELECT, MODIFY ON TABLE claraport_ws.prd_viasmiles_email.customer TO `d97d0f55-a968-43a0-94c6-5d433ac05874`;
```

4. Seed a test row:

```sql
INSERT INTO claraport_ws.prd_viasmiles_email.customer (fname, email) VALUES
  ('test', 'jvm@analyticsintellect.com');
```

> ⚠️ `db_utils.py` must use `auth_type="azure-sp-m2m"` (not `"azure-client-secret"`). A wrong value fails silently and the connector falls back to interactive browser OAuth, hanging forever on a headless server.

## 4. ACS email delivery — required setup

1. Assign the service principal the **Communication and Email Service Owner** role on the Communication Services resource (Access control (IAM)) — Contributor is not sufficient.
2. Create an **SMTP Username** under the Communication Services resource's SMTP Usernames blade, linked to the Entra app (`ViaSmile-Smtp` in this project).
3. The SMTP password is the **raw Entra client secret itself** — not an MSAL access token. ACS does the token exchange on its own backend using the app linked to the SMTP username.

## 7. Monitor & verify

Communication Services resource → **Diagnostic settings** → send `EmailSendMailOperational` and `EmailStatusUpdateOperational` to a Log Analytics workspace, then query:

```kql
ACSEmailStatusUpdateOperational
| where TimeGenerated > ago(1h)
| project TimeGenerated, MessageId, Sender, Recipient, Status, StatusDetail
| order by TimeGenerated desc
```

`Status` resolves to `Delivered`, `Bounced`, `Failed`, `Suppressed`, or `Quarantined`.

## Common issues

| Symptom | Cause | Fix |
|---|---|---|
| Chromium sandbox crash on `az login` | Browser can't launch as root headless | `az login --use-device-code` |
| `func: command not found` | Core Tools not installed | Install via apt (see above), not npm |
| `TABLE_OR_VIEW_NOT_FOUND` | Schema/table missing in Unity Catalog | Create schema/table, grant access |
| Hangs at "Listening for OAuth callback" | Wrong `auth_type` value in `db_utils.py` | Use `"azure-sp-m2m"` |
| `403 Forbidden` on Databricks `OpenSession` | Service principal not added as workspace identity | Add under Admin Settings → Identity and access |
| `PERMISSION_DENIED`, not authorized for SQL Endpoint | Missing "Can Use" grant on warehouse | Grant on warehouse's Permissions tab |
| `535 5.7.3 Authentication unsuccessful` | Wrong sender address, wrong role, or sending an OAuth token instead of the client secret | Use verified MailFrom address; assign "Communication and Email Service Owner"; pass the raw client secret as the SMTP password |
| `AADSTS7000215` invalid client secret | Vault holds the Secret ID, not the Secret Value | Regenerate secret, copy the Value column |
| Local script fails with `KeyError` on env vars | App settings from `local.settings.json` not exported into the shell | `export` each `ACS_*`/`KEY_VAULT_URL` var, or run through `func start`/Core Tools which loads them automatically |
| Connection refused on 2nd+ SMTP send in a loop | ACS SMTP relay throttling rapid repeated connections | Add a short delay (e.g. `time.sleep(2)`) between sends |
